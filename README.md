# Avafem Brand Connect

A local sandbox for Avafem brand onboarding, catalog review, fulfillment Bags, dashboard handoffs, API/MCP access and simulated settlement. Its separate My Store 2 provider-test panel has completed one actual Stripe test payment, Stripe Tax transaction and Shopify test order, with independent order readback and duplicate-prevention replay. This limited one-store exercise is not a production marketplace, general shopper checkout or passed three-store acceptance gate.

The owner-only three-store TEST cash lifecycle is now **completed**: one actual Stripe charge, three PAID Shopify test orders with stock decrement, partial shipments/test delivery, refunds/reversals, and three worker-created bank TEST payouts with actual `paid` readbacks. A separate three-store cancellation run is fully refunded and cash-reconciled. The approved **two-cent platform-only tax-rounding memo is recorded**, preserving the raw difference with zero unexplained cents and no cash changes. Settlement/payout automation remains opt-in per immutable run policy, not enabled by default. **Full acceptance remains false**: Tax evidence is an explicitly frozen dashboard observation, not live Tax API certification, and the local-only limitations below remain. See the current evidence checkpoint below.

The user chose **local-only testing**: no public tunnel is authorized or running. Local polling can reconcile checkout/Shopify changes; real webhook delivery and public OAuth callbacks remain untested. The isolated app test clock simulates the return-window hold, not provider/calendar time. Shipping notices use a simulated inbox, not external email delivery. Never point a tunnel at the owner dashboard on port 4317; the optional webhook-only proxy is not started automatically.

## Run locally

Requires Node.js **24 or newer** and npm. Run these commands from this project directory:

On this Mac you can also double-click **Start Avafem.command**. It checks Node, installs locked dependencies if needed, builds the dashboard and starts the local server. Keep its Terminal window open while using the app; Control-C stops it. The launcher does not deploy or expose the app publicly.

```sh
npm ci
npm run build
npm run check
npm test
npm start
```

Open **http://127.0.0.1:4317**. The server serves the built React app from `dist/`; rebuild after frontend changes. `/health` reports the sandbox mode and database type. Stop the server with Ctrl+C.

For development, run `npm run dev` for the watched backend. In a second terminal, run `npm run dev:web` and open http://127.0.0.1:5173. Vite proxies API, OAuth and MCP requests to the backend on port 4317. Provider webhook endpoints and OpenAPI documentation should be called directly on port 4317.

The default listener is loopback only. On that local listener, `/api/session` creates a workspace-owner browser session; this is a local development convenience, not a public sign-in system. Owner sessions can switch between Operations and brand previews. Invitation links create a brand-scoped session that cannot switch into Operations. Browser mutations require the session cookie and `X-CSRF-Token`; brand integrations use scoped bearer credentials instead.

## Storage and configuration

The default database is **PGlite**, an embedded PostgreSQL-compatible engine. Data persists in `.runtime/postgres`. No PostgreSQL server is required. On first startup, the app also creates `.runtime/local-secrets.json` with local session/encryption keys and seeds three synthetic brands and their sample order. Seeding is idempotent; restarting preserves your changes.

To use a separate PostgreSQL database, set `DATABASE_URL` to a database dedicated to this sandbox before starting. The app creates/migrates its own tables. Tests explicitly use isolated in-memory databases and injected provider adapters.

`server/start.mjs` loads an optional root `.env`. You can copy `.env.example` for local configuration. Keep real credentials out of source and chat.

| Variable | Purpose / default |
|---|---|
| `HOST`, `PORT` | `127.0.0.1`, `4317` |
| `AVAFEM_MODE` | Must be `sandbox`; other modes are rejected |
| `DATABASE_URL` | Optional PostgreSQL connection; otherwise PGlite |
| `AVAFEM_SESSION_SECRET` | Optional local override; otherwise generated in `.runtime` |
| `AVAFEM_CREDENTIAL_ENCRYPTION_KEY` | Optional local override; keep stable to decrypt stored webhook data/secrets |
| `AVAFEM_ADMIN_TOKEN` | Owner credential for `/api/admin/session` when automatic local bootstrap is disabled |
| `AVAFEM_ALLOW_LOCAL_BOOTSTRAP` | Set `false` to disable the automatic loopback owner session |
| `SHOPIFY_SHOP`, `SHOPIFY_CLIENT_ID` | Default to the existing My Store 2 test integration described below |
| `SHOPIFY_CLIENT_SECRET` | Optional secret supplied through environment rather than macOS Keychain |
| `SHOPIFY_ACCESS_TOKEN` | Optional existing token for the configured shop; `SHOPIFY_AVA4_TOKEN` is a legacy compatibility alias |
| `SHOPIFY_WEBHOOK_SECRET` | Optional Shopify HMAC secret override; normally the app client secret |
| `STRIPE_SECRET_KEY` | Real Stripe **test** secret key; absent means unavailable, not simulated connectivity |
| `STRIPE_WEBHOOK_SECRET` | Signature secret for the Stripe endpoint |
| `PUBLIC_BASE_URL` | Optional future HTTPS origin/metadata setting; it does not deploy a server or create callbacks |

API keys/invite tokens are stored as hashes. Offline Shopify access/refresh tokens, Bag shipping addresses, shipping-bearing outbox fields, private dispatch bodies/capability URLs, idempotency responses, raw inbound provider payloads and outbound signing secrets use application AES-256-GCM encryption in the running app. Startup backfills the older logical rows. Domain-only tests can deliberately inject plaintext fixtures. This is **not whole-database, disk or backup encryption**, and migration cannot erase plaintext from historical WAL/MVCC versions or backups. Original local fixtures were synthetic. Treat `.runtime` and its encryption keys as private together. Changing the encryption key makes previously encrypted rows unreadable; shipping reads fail closed without the correct key.

## What to try

1. Open the Operations dashboard and inspect the seeded brands, products and three Bags. The sample order totals **$106.29**, with simulated brand shares of **$32.20 / $25.52 / $27.91**.
2. Edit a catalog product. Required fields and evidence are validated; claim/content changes require human review before approval. Price and stock edits preserve approval when the remaining product is valid.
3. Create a sandbox order from approved, stocked products. Each brand receives its own Bag. Inventory, balanced ledger journals and outbox events commit together.
4. Run jobs from the dashboard, or `POST /api/jobs/run` as the owner. Inspect the dashboard dispatch inbox and open the generated `/handoff/<token>` link. It is a limited, expiring shipping capability for one Bag; successful submission consumes it. It cannot open the Operations workspace.
5. Record one complete shipment, then use the owner-only sandbox delivery action. Delivery schedules simulated settlement **after the return window** (new default 30 days), never earlier than the longer snapshotted/current brand policy, the seven-day minimum, or an already-promised later date. Policy reductions cannot shorten existing holds. It does not contact a carrier. Due settlement and credit-release jobs run once.
6. Request a refund as the brand. This creates a **proposal**; only the owner can approve its simulated accounting. Pending proposals hold settlement. These original synthetic-domain controls accept full-Bag refunds and one complete shipment per Bag. The separate provider-bound three-store workflow implements item-level partial fulfillment/refunds and cancellation; its actual-provider acceptance is still incomplete.

From a brand's onboarding controls, the owner can create an invitation with `POST /api/brands/:id/invite`. The returned `/onboard/<token>` path expires after 48 hours and can be accepted once. Acceptance records agreement to a **sandbox draft**, not a final legal brand agreement. Keep invite and handoff URLs private; possession grants their limited access.

Email sending is not connected. The dispatch inbox stands in for email delivery, and exposes the handoff link for local testing. The worker suppresses stale handoffs when a Bag is refunded or on refund hold. Remote Shopify dispatch requires its own exact mapping/reconciliation safeguards.

## Architecture

| Component | Responsibility |
|---|---|
| `web/` | React operations and brand UI, invitation and shipping-link entry pages |
| `server/app.mjs` | Fastify HTTP routes, raw webhook bodies, browser sessions/CSRF, tenant/scoped API access |
| `server/auth.mjs` | Hashed credentials, one-hour API tokens, invitations, encryption, rate limits and idempotency |
| `server/domain.mjs` | Brand/catalog rules, canonical Bags, shipments, full refunds, simulated double-entry ledger |
| `server/operations.mjs` | Imports, connector state, persistent outbox/delivery jobs, provider inbox and handoffs |
| `server/unified-checkout.mjs`, `server/test-stores.mjs` | Frozen three-store test checkout, manual-capture checks and immutable provider/store mappings |
| `server/provider-fulfillment.mjs`, `server/provider-money.mjs`, `server/provider-events.mjs` | Provider-bound item fulfillment, refunds/cancellation, separate transfer/payout operations and inbound-event reconciliation |
| `server/provider-jobs.mjs`, `server/provider-reconciliation.mjs`, `server/provider-automation.mjs` | Local polling, provider-to-ledger checks and explicitly enabled per-run settlement/payout policies |
| `server/integrations/` | Shopify/Stripe adapters, explicit payload projections, HMAC and public HTTPS destination checks |
| `server/mcp.mjs` | Streamable HTTP MCP tools backed by the same scoped domain actions |
| `server/db.mjs`, `server/schema.sql` | PGlite or PostgreSQL storage and transaction boundaries |

Jobs run every five seconds while the server is running. The manual run button uses the same worker path. Outbox work uses persisted attempts and processing leases; outbound webhooks retry transient failures with backoff for up to 72 hours. Permanent destination errors fail for operator review. Replay is explicit. A stopped local app cannot run jobs.

Provider settlement and external payouts remain manual by default. An owner may explicitly enable TEST-only automation for one immutable run, bound to the approved platform, its three exact recipients and named post-transfer refund gates. It rechecks policy inside the durable money lease and retains delivery/return-window, refund and reconciliation holds. Payout gates require the named actual Stripe refund, matching Shopify bookkeeping and verified brand-share reversal. Automation does not ship, initiate refunds, advance the test clock or send external email; uncertain outcomes remain held rather than generating replacement operations.

## Brand API, OAuth and MCP

Create a brand API key or OAuth client from the owner workspace's brand credentials controls, or `POST /api/brands/:id/credentials`. Secrets are shown once. Static keys start with `avf_test_`; OAuth clients exchange their ID/secret at `POST /oauth/token` using `grant_type=client_credentials`. Tokens last **one hour** and cannot expand the client's granted scopes. Revoking a credential also disables tokens issued from it.

Scopes are `catalog:read`, `catalog:write`, `orders:read`, `orders:fulfill`, `payouts:read`, and `refunds:write`. Every credential is bound to one brand. The API rate limit is 10 requests/second per brand, burst 30; 429 responses include `Retry-After`. All `/v1` POST mutations require `Idempotency-Key`; the key/body result is retained for 24 hours per brand and endpoint. Reusing a key with a different body returns 422. A pending outcome returns 409 and requires reconciliation. PUT/PATCH routes are not covered by this POST key store.

Open http://127.0.0.1:4317/openapi.json for the current API document. Runnable request shapes with fake placeholders are in [examples/brand-api.http](examples/brand-api.http). Main resources include:

- `/v1/products`, `/v1/products/:sku`, `/v1/products/import`, `/v1/inventory/:sku`.
- `/v1/bags`, `/v1/bags/:id`, and Bag `/shipments` and `/refunds` POST routes.
- `/v1/payouts`, `/v1/payouts/summary`, `/v1/webhook-endpoints` and endpoint `/replay`.
- `/v1/sandbox/orders` for a synthetic order scoped to the authenticated brand.

The MCP endpoint is **POST `/mcp`** with the same bearer authority. Send `Accept: application/json, text/event-stream`; it supports standard JSON-RPC `initialize`, `tools/list`, and `tools/call`. GET is not an SSE subscription and returns 405. Discovery metadata is at `/.well-known/oauth-protected-resource` and `/.well-known/oauth-authorization-server`.

Tools include `list_awaiting_shipment`, `get_bag`, `get_payout_summary`, `get_catalog_issues`, `onboard_brand`, `mark_shipped`, `update_inventory`, `import_products`, and `refund_order`. Write tools require an `idempotencyKey` argument. `refund_order` only submits a human-reviewed proposal; no MCP tool approves refunds or moves money. No shopper checkout tool is exposed to brands.

Outbound webhook envelopes carry `sandbox:true`, an event ID and allowlisted data. Verify `Avafem-Signature: t=<seconds>,v1=<hex>` as HMAC-SHA256 over **`timestamp + "." + exact raw request body`**, with a five-minute timestamp tolerance. Deduplicate the event ID after signature verification. Registration accepts public HTTPS destinations; private/reserved addresses and redirects are blocked, and delivery pins a validated IP to prevent DNS rebinding. Registering an endpoint can cause the worker to make real HTTPS delivery attempts—use an endpoint you control.

## Shopify test connector

The existing own-store test configuration targets `i4vd1u-s8.myshopify.com` and client ID `e4d70eed35b16d38f81e3af32a35dd65`. On macOS the adapter can read its existing app secret from Keychain service `co.avafem.shopify.i4vd1u-s8.client-secret`, account equal to that client ID. This project contains **no secret** and does not create a Keychain entry. Another machine needs separately configured credentials and an installed app. If credentials are absent, the connector reports unavailable.

Own-organization client credentials yield expiring backend tokens, cached in memory and renewed before expiry. The app and store must belong to the same Shopify organization. That flow does not onboard unrelated brands.

Per-brand offline authorization-code OAuth is now implemented in `server/shopify-connections.mjs`: hashed durable browser/store-bound state, exact scope ceiling, encrypted token pairs, serialized acquisition/refresh, one-use callbacks, same-brand/store reinstall, and uninstall revocation. Configure **server-only** `SHOPIFY_OAUTH_CLIENT_ID`, `SHOPIFY_OAUTH_CLIENT_SECRET`, and an HTTPS `PUBLIC_BASE_URL` whose `/oauth/shopify/callback` URL is registered on that Shopify app. This does not create/expose a public server or expand the remote app's permissions automatically. Disable local bootstrap and configure owner authentication before exposing any listener. The app secret and server keys must never enter frontend code.

An owner/CSRF-protected `POST /api/brands/:id/shopify/authorize` with `{ "shop": "the-brand.myshopify.com" }` returns the authorization URL and sets an HttpOnly/Secure/SameSite-Lax callback cookie. The callback saves only that bound brand's tokens, never creates an owner session, and returns redacted metadata. `GET /api/brands/:id/shopify` shows scoped status; owner `POST /api/brands/:id/shopify/import` reads that specific store. These routes are API-level foundations, not a completed self-service onboarding UI. An invalid/expired refresh pair is cleared and requires reauthorization; transient failures retain the encrypted pair. Token network exchanges are deliberately serialized with DB mutations in this initial implementation; use per-store locking before production scale.

The owner can explicitly run preflight and catalog import from Connections. These perform real read-only Shopify API calls when credentials are available. Imported products enter validation/review; incomplete variant pagination is reported rather than silently listed. API version is pinned to `2026-10`. Expected scopes are:

```text
read_products,write_products,read_inventory,write_inventory,read_orders,write_orders,read_draft_orders,write_draft_orders,read_fulfillments,write_fulfillments,read_merchant_managed_fulfillment_orders,write_merchant_managed_fulfillment_orders,read_shipping,read_customers,write_customers
```

This is the exact approved scope ceiling; `read_locations` is not requested. On October 18, 2026 (America/Chicago), version `avafem-test-v2-exact-scopes` was released and the existing My Store 2 installation was reauthorized through Dev Dashboard **Install app → Update data access**. Fresh Admin API preflight verified all 15 scopes with no missing or unexpected grants; `read_locations` is gone. The existing test order's address and email were also readable, without printing them. No uninstall or store-order deletion was needed. Shopify write scopes imply their matching read permission. These results verify this one installation, not the three-store OAuth acceptance requirement or production privacy compliance.

Only these seven webhook topics may be subscribed: `orders/updated`, `orders/cancelled`, `refunds/create`, `fulfillments/create`, `products/update`, `inventory_levels/update`, `app/uninstalled`. No delete or later fulfillment-update subscription is silently added. Catalog deletion and later tracking convergence have polling/diff reconciliation paths whose actual-provider acceptance remains incomplete. Provider-bound order/refund/cancellation ingestion is implemented using authoritative readbacks and exact run/store mappings; legacy, unmapped or unverified accounting events remain visibly `requires_review`, not falsely completed. Per-brand webhook routing is isolated by the installed shop/brand; uninstall clears that brand's token and pauses its listings, while an event older than the new installation cannot clear a newer pair. Real webhook delivery remains untested under the user's local-only choice.

For explicit test order pushes, durable reservations also limit each store to five new creation attempts in a rolling minute. Reconciliation reads/replays never reserve a second creation slot for the same Bag. Do not bypass Shopify throttling with a second order/fallback.

An explicit owner `POST /api/bags/:id/push-shopify` is an external write, not a seed/job side effect. It is test-only, uses both Shopify test flags, no customer receipts, relay email, stable short tags, Bag source identifiers, and `BYPASS` inventory. Exact variants must be mapped. Taxable Bags are blocked until authoritative tax lines exist; the local 8.25% fixture must not be pushed as a real tax calculation. A timeout/uncertain response is persisted for reconciliation and never automatically retried or switched to a second fulfillment path. There is no general native order-create idempotency guarantee.

`POST /webhooks/shopify` checks raw-body HMAC and store identity, deduplicates delivery IDs and retains encrypted payloads before worker processing. Subscription registration is an explicit adapter operation and is not done at startup. Public callbacks require separately configured HTTPS access. The provider-bound lifecycle supports partial quantities; unmapped or uncertain fulfillment/refund evidence requires review.

## Stripe and money boundaries

**The original dashboard test bags, transfers, ledger journals and Beauty Bank credit values are synthetic.** Their tax is a fixed **8.25% sandbox fixture on merchandise**, not a Stripe Tax calculation, tax advice or a valid assumption for real product categories/shipping. No card is charged when creating a sandbox bag. A simulated `paid` or `payoutsEnabled` state is not proof of a real Stripe account or payment. The separate **Connections → My Store 2 provider test checkout** panel is explicitly different; it never creates synthetic Bags, ledger entries or simulated payouts as evidence of a Stripe payment.

The official SDK adapter includes test Accounts v2 Express recipients/onboarding links, separate connected-account BalanceSettings manual-payout setup, explicit tax calculations/transactions/reversals for the one-store path, hosted Checkout native tax for the unified path, shipping-bearing PaymentIntents, separate transfers using `source_transaction`, refunds, transfer reversals and raw signature verification. New recipient IDs are saved before payout-schedule setup; an uncertain setup never authorizes replacement account creation. Missing Stripe credentials mean unavailable; API status never fabricates a real connection. Live keys are rejected by default, and this app's configuration is sandbox-only. No agreement acceptance or KYC completion is fabricated by the adapter.

The masked **Configure test credentials** form accepts only a Stripe secret test key and an optional webhook signing secret. It verifies account access read-only, keeps keys only in server process memory, and clears them on server restart. Keys are not written to project files, the database, browser storage or logs. Never paste keys into chat. The form uses an owner browser session, CSRF protection and a loopback-only endpoint.

The separate provider-test checkout freezes one eligible My Store 2 variant and a synthetic address, obtains an actual Stripe Tax quote, then requires explicit confirmation to pay with the official test Visa PaymentMethod. It verifies the retrieved test PaymentIntent before creating exactly one Shopify test order, reads back totals, items, shipping address and test transaction flags, and records the Stripe Tax transaction. Stable run IDs, encrypted snapshots, a durable dispatch reservation, shared five-order-attempts-per-minute budget and marker-based reconciliation prevent blind duplicate orders. No live card details are accepted. Shipping is a zero-dollar test fixture; `txcd_99999999` (**General - Tangible Goods**) is an explicit integration-test classification, not a classification of real merchandise. This one-store provider test does not prove inventory decrement (`BYPASS`), shopper address capture, webhook delivery, split-brand orders or settlement. See [the local test-checkout contract](docs/test-checkout.md).

These provider workflows are **not general shopper checkout or a substitute for the original synthetic accounting**. The three-store test panel implements connected-recipient onboarding and provider-to-ledger reconciliation; the earlier one-store test panel does not. `POST /webhooks/stripe` verifies signatures using `STRIPE_WEBHOOK_SECRET`, deduplicates and encrypts the payload. Exact provider-bound checkout/payment events can trigger authoritative reconciliation, while unrelated or unsupported events require review. Events do not silently create synthetic payments or bypass explicit money-policy gates. No real webhook delivery is claimed for this local-only run.

Shopper refunds and recovery of the brand share are distinct amounts. The provider-bound service preserves a successful shopper refund together with a recovery error/receivable if transfer reversal fails. Immutable checkout/account mappings, durable intents, balanced booking and reconciliation guards are implemented for the bounded test workflow. Owner-origin refunds compare native Shopify quantity/tax/shipping suggestions with the frozen allocation before Stripe money moves; mismatches hold for review. These implementations do not certify actual-provider acceptance or production refund/tax policies. The prototype makes no merchant-of-record, tax-registration or legal eligibility decision.

### Separate platform tax-rounding reconciliation

The owner-only Tax report is separate from cash reconciliation. An immutable mapping binds the existing checkout/refund IDs to native Stripe Tax transactions. Read-only TEST API retrieval, complete bounded line pagination, exact payment/refund references, original/reversal links, and native Shopify refund readbacks establish the evidence. Missing evidence, outliers, or contradictory references remain review holds; an operator assertion alone cannot replace proof.

**Stripe-managed Checkout Tax limitation:** the actual API returned HTTP 404 for the existing Checkout Tax transaction, explicitly stating that it is Stripe-managed and only caller-created transactions can be fetched. These existing records are still visible in the authenticated sandbox Tax dashboard. For the two approved existing test runs only, a source-reviewed, SHA256-locked dashboard snapshot can supply their observed IDs, references and totals. The report explicitly marks this as **a frozen dashboard observation, not a live Tax API audit**; it does not invent Tax line items or native `original_transaction` links. Fresh charge/refund API and native Shopify checks remain required. Snapshot evidence older than 24 hours requires review; the nightly worker cannot manufacture a fresh Tax observation. Live, malformed or unrelated API failures never activate this fallback.

The approved test policy is restricted to the two existing three-store runs and their exact Stripe sandbox. An explicit acknowledgement can record a balanced, immutable **platform-only memo subledger** for differences of at most one cent per refund. It does not change the core cash ledger, tax payable, shopper refund, brand recovery, commission, transfer or bank payout; it makes no filing or legal tax-classification decision. The report retains the raw Stripe-versus-Shopify difference alongside the recorded variance and remaining unexplained amount. Stable operation IDs and evidence hashes prevent duplicate/conflicting entries. The nightly worker refreshes configured evidence but never posts an adjustment automatically. `fullAcceptancePassed` remains false.

Local-owner endpoints are `POST /api/unified-checkout/:id/tax-evidence`, `POST /api/unified-checkout/:id/tax-reconciliation-report`, `GET /api/unified-checkout/:id/tax-reconciliation-report/:reportId`, and `POST /api/unified-checkout/:id/tax-rounding`. All require a loopback owner browser session; mutations also require CSRF. The acknowledgement accepts a report ID/hash and stable operation ID, **not caller-supplied cents**. Brand API credentials cannot access this evidence or subledger.
